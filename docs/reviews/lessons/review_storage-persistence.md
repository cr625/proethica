## Question 2. Behaviour the rules do not name

### Fixed on the review branch

1. **The stored type of a matched individual pre-empted the honoring guards of the commit.** `app/services/extraction/extraction_graph.py`, `individual_type_iri` (line 292). `pydantic_to_rdf_data` wrote `rdf_json_ld.types = [matched_uri]` for every individual whose `match_decision.matches_existing` held a full IRI. Both TTL writers (`ontserve_commit_service._commit_individuals_to_case_ontology` line 680, `versioned_commit._write_case_ttl_fresh` line 510) call `_matched_class_override(rdf_data, concept_cat, type_uris)`, which returns None when `matched_local in minted_locals` ("already typed to the matched class; nothing to honor", `category_resolution.py` line 194), before its confidence floor (line 172, the commit-definitions lesson, `match_policy.match_link_threshold`, default 0.85), its sanitizer round-trip check (line 183) and its chain-category check (line 196). The commit then writes `type_uris` unchanged. For an individual whose matcher link was wrong this meant: (a) a sub-floor link (0.75, "matched to parent with medium confidence", for example the Legal Obligation match of class row 95622 that the cascade in `matching.py` copies onto individual 95625) was typed to the matched class in the store and in the TTL, where the commit-definitions test `test_below_floor_keeps_the_minted_type_in_both_stores` expects the minted class in both; (b) a link to a core# or concepts# class (both in the curated matcher vocabulary, `_curated_only`) was stored under that namespace, and the commit, which mints every type IRI in the intermediate namespace from the local name (line 692), declared a new class `intermediate#Obligation` or `intermediate#NonDeception` as genuinely new (the resolver knows neither local name), the case the round-trip guard was written for; (c) a link to a class whose chain resolves to another category than the component was typed to it, and the materialized direct type followed the chain (`resolved_cat = established`, line 741, a warning only), where the override would have kept the minted class. The cross-category gate of the matcher drops resolvable cross-category matches before storage, so (c) is confined to links whose chain the resolver cannot settle; (a) and (b) were caught nowhere. Fix: `individual_type_iri` adopts the matched IRI only when the decision links the row by the shared policy (`linked_existing_class` with `match_link_threshold()`), the IRI is `INTERMEDIATE_NS` plus its local name, and `naming.safe_local_name(local) == local`; otherwise the class reference is minted, as for an unmatched individual, and the commit applies its rule to the row as to every other row. Tests: `tests/unit/test_storage_persistence_review.py` (4 tests; they fail at the integration tip and pass on the review branch). For the decision on the laptop: the correction of D-22 in the review log wants individual 95625 typed LegalObligation (the 0.75 match), which the commit-definitions floor declines; the fix follows the floor. Lowering `PROETHICA_MATCH_LINK_THRESHOLD` or accepting the minted type are the two ways to reconcile the lessons.

### Reported, not changed

2. **The chain-category check is still skipped for a linked individual.** `category_resolution.py`, `_matched_class_override` (line 194). After the fix, an individual linked at or above the floor to an intermediate-namespace class whose chain the resolver resolves to another category, or cannot resolve, is typed to it in the store and in the TTL; the override returns before `_established_core_category`. The matcher gate (`matching.py`, `_apply_cross_category_gate`) keeps a match whose chain is unresolved, the override refused to honor it, and the merged code sides with the matcher for these rows. Proposed: run the floor and chain checks whenever `match_decision` names an existing class, and on failure re-mint from the class reference of the row (`properties.<concept>Class`, which `_individual_class_ref` in the reconciliation service already reads as a fallback) instead of returning "nothing to honor".

3. **The consolidation card shows the new activities as pipeline runs of their own.** `rdf_storage_service._record_storage_provenance` passes `session_id=extraction_session_id` (the extraction uuid) to the merge and the guard activity. `helpers.group_consolidation_by_run` (provenance-surfaces) makes one run per session id, labels it "Pipeline run <session id>", and attaches only session-less activities to the nearest run by time. The extraction-time filter passes (`extractor.py` lines 256, 298 and 339) record no session id and attach forward. Each pass that merged or refused therefore appears as a separate group labelled with its extraction uuid, beside the real run (PipelineRun id). The branch test asserts the session id, a deliberate choice that ties the activity to its prompt row, so it was left. Proposed: in the grouping, treat as a run only a session id that is a PipelineRun id and attach the others by time like the filters; or record the extraction session in `execution_plan` and pass no session id.

4. **MutableDict coerces at load, so a legacy row whose JSON column holds a non-object fails to load.** `app/models/temporary_rdf_storage.py` (lines 50 and 85), `app/models/case_precedent_features.py` (line 72). `Mutable.coerce` raises `ValueError` for a value that is not a dict and not None, on assignment and in the load and refresh listeners. Every current writer passes a dict or None (the step 1 to 4 writers, `apply_corrected_quotes`, the raw-SQL `COALESCE(..., '{}'::jsonb) ||` writers of `extraction_metadata`), and the history holds no `json.dumps` write to these columns, so the exposure is rows written by code no longer in the tree. Proposed: before deploying, run on the laptop `SELECT count(*) FROM temporary_rdf_storage WHERE jsonb_typeof(rdf_json_ld::jsonb) <> 'object' OR jsonb_typeof(provenance_metadata::jsonb) <> 'object'` and the same for `case_precedent_features.extraction_metadata`, and repair any hit; a hit would raise on every query that returns the row.

5. **The two sanitizers differ for more than the hyphen.** `naming.safe_local_name` keeps ASCII letters and digits only; the former `_sanitize_label` kept hyphens, periods, slashes, colons, semicolons, underscores and non-ASCII letters ("Code Section III.1.b" gave CodeSectionIII.1.b and now CodeSectionIII1b, "Café Owner Role" gave CaféOwnerRole and now CafOwnerRole, "BER Case 22-5" gave BERCase22-5 and now BERCase225). Class rows stored before the branch keep the old-form `entity_uri`; a later pass of the same case (a discussion rerun) merges its classes into those rows by label and types its new individuals with the new form, so within one case the IRI of a class row and the type IRI of its individuals can differ for such labels until the row is re-extracted. The commit re-sanitizes both, so the TTL is unaffected; the reconciliation rename map is keyed by the class row IRI, so such an individual is not repointed when its class is canonicalized. `domain_config.sanitize`, which the merge-guards veto uses as the label-derived base (`entity_reconciliation_service.py` line 1067), still mirrors the old sanitizer; the veto also checks `entity_uri` and the matched class, so the label base matters only for a merged row carrying another IRI. Proposed: point `domain_config.sanitize` at `naming.safe_local_name` (merge-guards cluster), and expect the drift on cases re-run after the branch.

6. **A flush failure inside the provenance recorder is logged at DEBUG.** `rdf_storage_service._record_storage_provenance` flushes the session (for the surviving row ids) inside a try whose except logs at debug level; a flush error there surfaces as a commit failure in the caller with the cause hidden. Proposed: flush outside the try, or log the except at WARNING with `exc_info`.

### Checked and found consistent

- Both production loops in `store_extraction_results` pass `storage_type` and a trace; no other caller of `_find_existing_entity` or `_find_semantic_match` exists. The unscoped `find_existing_entity` of the merge service is reached only through `save_or_merge_entity`, which has no production caller; the reconciliation service uses `merge_entity_properties` only.
- `storage_summary` scopes by case, session and extraction type. `extract_concept`, the single extraction entry point (called by `pipeline_tasks.run_extraction` without a session id), generates one uuid per concept and pass, and `store_extraction_results` stores rows under that session, so `stored_*` counts the rows of this pass and the merged rows (which keep their own session id) make up the difference. The `TemporaryRDFStorage.store_extraction_results` wrapper commits before step 5, so the summary is a second commit; a failure there leaves the extracted counts of step 1 on the row, as the code says.
- The new summary keys are additive. `_parse_results_summary` and the funnel reader use dict access and ignore unknown keys; `provenance.js` renders no step 1 or 2 summary field directly.
- `_record_llm_query_provenance` (provenance-surfaces) runs between the prompt save and storage, commits on its own and does not touch `results_summary`; `prompt_row` reloads transparently after that commit.
- `_merge_into_existing` and `EntityMergeService.merge_entity_properties` reassign the same dict and call `flag_modified`. The other in-place editors of the two `TemporaryRDFStorage` JSON columns (obligation_engagement_apply, temporal_sequence_apply, citation_provenance_apply, the corrected quotes of the gate in pipeline_tasks, `entity_mgmt`, the reconciliation renames) copy the dict before editing, so none depends on MutableDict and none mutates a nested structure in place. The one top-level in-place edit without a flag (`keep_entity.rdf_json_ld['label'] = preferred`, reconciliation line 274) runs after `merge_entity_properties` flagged the column and is tracked by MutableDict now.
- `MutableDict.as_mutable(db.JSON)` instantiates its own type object per column, so the other JSON columns keep plain JSON behaviour. `isinstance(x, dict)` holds for a MutableDict, and no `type(x) is dict` check exists.
- The merged `phase4_connector` refreshes the outcome before the metadata block and writes scalar columns only; the metadata block edits the same MutableDict and flags it, so a rerun writes `phase4_connected_at` and the narrative counts.
- The route IN-list ('merge' beside 'gate' and 'repair') and the JS style map are unions of the two branches' entries; `summarizeResult` renders the `merges` and `kept_separate` lists generically (count plus the first labels).
- The individual schemas of the seven step 1 and 2 concept types derive from `BaseIndividual` and carry `match_decision`; the cascade in `matching.py` copies the resolved `matched_uri` and the confidence of the class onto the individual, so the floor applied in `individual_type_iri` reads the confidence the commit reads.
