## Question 2. Behaviour the rules do not name

### Fixed on the review branch

1. **The consolidation card split one pipeline run into many.** `app/routes/provenance/helpers.py` (`group_consolidation_by_run`, line 687) and `app/routes/provenance/pipeline_routes.py` (the consolidation query, lines 156 to 163). The helper took every session id for a pipeline run id. On the branch alone that held: the only sessioned rows of the queried types were the `_record_pass` rows of `app/tasks/pipeline_tasks.py` (line 271, `session_id=str(run.id)`), and the extractor's filters carry no session id. The integration merge added `merge` to the query's type list for storage-persistence, whose `_record_storage_provenance` (`app/services/entity/rdf_storage_service.py`, lines 395 to 445) records `storage_dedup_merge` (type `merge`) and `designator_guard` (type `filter`) with the extraction session id of one concept pass, the UUID `extract_concept` mints per concept and section (14 per run). Scenario: any pipeline run on the merged code in which a storage pass merged a row or refused a merge. Every such concept pass opened a "Pipeline run <uuid>" header of its own, newest first, and its rows left the run they belong to; the real run kept only its `_record_pass` rows and the commit-time passes. Fix: the route reads the PipelineRun ids of the case (`SELECT id FROM pipeline_runs WHERE case_id`) and passes them as `run_ids`; a session id outside the set is attached by time like a row without one, and the extraction-time types (`EXTRACTION_TIME_TYPES`, `filter` and `merge`) attach forward to the run that starts after them. A call without `run_ids` keeps the branch behaviour, so the branch tests stand. The header of a leftover cluster now reads "Activities outside a recorded pipeline run", since an extraction that never reached a run-scoped pass lands there as well as a commit made outside a run. Tests: `test_storage_dedup_rows_of_a_concept_pass_attach_to_the_pipeline_run`, `test_a_merge_row_before_the_next_run_attaches_forward_not_to_the_run_before`, `test_an_extraction_that_never_reached_a_run_scoped_pass_clusters_on_its_own`, `test_run_ids_are_compared_as_strings`, `test_without_run_ids_every_session_id_opens_a_run_as_before`.

2. **The truncation badge missed the phase 4 narrative prompts.** `app/routes/provenance/helpers.py` (`truncation_limit`, line 657). Commit 35a80006 (2026-07-11), which L5 cites, removed two slice forms: `text[:10000]` on nine prompt and response writes, and `text[:9950] + "\n... [truncated]"` on the three phase 4 narrative prompt writes. The flag covered the first form only. Scenario: a `phase4_narrative` row written before 2026-07-11 whose joined prompt exceeded 10000 characters, stored as 9966 characters ending in the marker (the July run of case 8 predates the commit). The card showed no badge on the one prompt whose text announces its own cut. Fix: a text ending in the marker is flagged at the length before it (9950); the badge title says the text was cut at that length by a storage slice. Tests: `test_truncation_limit_flags_the_marker_form_at_the_length_before_the_marker`, `test_stored_text_truncation_reports_a_marker_prompt`.

### Reported, not changed

3. **The secondary match can attach a storage pass to a model call.** `app/routes/provenance/helpers.py`, `_get_provenance_for_prompt` (lines 594 to 599). After the primary match (session id plus `dual_<concept>_extraction`) fails, the card takes any activity of the session and case. On the base no activity of the queried kinds carried an extraction session id, so the branch's reading of the rule held. With storage-persistence merged, `storage_dedup_merge` and `designator_guard` carry it (finding 1), so a prompt whose `llm_query` recording failed (the recorder is best-effort) while the storage pass recorded would show "rdf_storage_service, extraction_service, 0 ms" as the provenance of its model call. The two recorders run in one session a few statements apart, so the combination needs a failure specific to the recorder. Proposed: restrict the secondary match to `activity_type = 'llm_query'`, or exclude the pass types of the consolidation query.

4. **Two of the three round limits have no writer.** `app/routes/provenance/helpers.py`, `STORED_TEXT_LIMITS` (line 649). The history holds no slice at 20000 or 50000 (`git log -S":20000]"` and `-S":50000]"` over `app` return nothing); only `[:10000]` and `[:9950]` ever existed. A legitimate prompt or response of exactly 20000 or 50000 characters gets a badge that asserts a cut that never happened. The branch chose the values ("the larger values cover the same pattern at other round sizes"), the branch test pins them, and the chance of a hit is small. Proposed: keep 10000 alone, or name the two extra values as a guess in the comment.

5. **Interleaved runs.** `group_consolidation_by_run`, the window test. An unscoped activity that lies inside the windows of two run-scoped runs (two pipeline runs of one case overlapping in time) attaches to the run opened first, since a second distance of zero never beats the first. Deterministic, not chosen. Proposed: prefer the run whose nearest run-scoped activity is closest in time.

6. **The oldest run shown may be cut.** `app/routes/provenance/pipeline_routes.py`, `LIMIT 150` on the consolidation query (line 162), newest rows first. With the storage dedup rows a run holds 25 to 30 rows, so about five runs fit and the sixth loses its earliest rows while its header still reads as a whole run. Proposed: group first and limit the number of runs, or raise the limit.

7. **The quote stays a kept literal.** `field_classification._STRUCTURAL_KEYS` (line 260). The real producer leaves one top-level key that reaches the literal list: `source_text`, the quote, which the list also shows through `textReferences`. The rule names the bookkeeping keys and the type anchors, and the quote is content, so the card shows it twice. Recorded by `test_every_wrapper_key_the_producer_writes_is_structural_except_the_quote`. Proposed: decide whether `source_text` joins the set; if it does, `textReferences` keeps the quote on the card.

### Checked and found consistent

- The savepoint and the separate commit. `app/services/extraction/extraction_graph.py`, `_record_llm_query_provenance` (lines 319 to 367). `ExtractionPrompt.save_prompt` commits (`app/models/extraction_prompt.py`, line 106) before the recorder runs, as on the base, so no caller work is pending when the recorder opens its savepoint (line 346) and commits (line 364); the commit carries the activity, its agent and its two entities and nothing else. A failed flush inside the savepoint rolls back those rows only, the exception is caught, and the storage step runs on a clean session (`test_a_failing_provenance_recorder_never_costs_the_extraction_its_entities`). A storage failure after the commit leaves the activity in place, which the branch chose (the model call happened). A failure of the commit itself (a lost connection) is caught and logged, and the storage step then fails on the same connection as it would on the base. The Celery path runs `run_extraction` in threads with their own application context and scoped session (`run_extraction_parallel`), so the commit of one concept pass never carries another's rows.
- The temporal pass. `stage7_storage._store_llm_trace` passes the trace timestamps, prompt, response and metadata to `record_llm_query`, which flushes without committing, as the inlined code did; the stage commits afterwards as before.
- The call bounds. `UnifiedDualExtractor.extract` sets `last_llm_started_at` and `last_llm_ended_at` around `_call_llm` alone (lines 172 to 174); the precedent filter, the role checks and the individual-type judge run after the end stamp, so the recorded duration is the model call.
- `_determine_origin` honours a stored origin only when it is one of the four known values and falls back to the name heuristics otherwise; the recorder of this branch is the only writer of `activity_metadata['origin']` in `app`.
- L1 and the other cards. The temporal cards resolve their activity through their own lookup by case id and activity name (`_get_temporal_extraction_data`, lines 224 to 231), which the branch does not touch; `CONCEPT_ACTIVITY_MAP` has no step 4 names, so the step 4 cards never used the removed branch. Legacy rows: the February 2026 recorder (`step1_enhanced.py` at 5478d89e^) wrote `dual_<concept>_extraction` with the same session id it stored on the prompt row, so those cards still match through the session branch.
- L3 and the TTL. The commit emitter reads `properties` for its literal loop (`app/services/commit/ttl_emitters.py`, lines 433 to 434) and for the synthesis-literal marker (line 205), never the top-level keys, so `_STRUCTURAL_KEYS` cannot remove a literal from the TTL. The real producer writes the category copy as a duplicate of the camelCase property (`pydantic_to_rdf_data`, "commit service checks rdf_data.get(category_field) as fallback"), and the property stays a content literal on the card for all six concept types (`test_the_real_class_record_hides_its_wrapper_keys_and_keeps_the_category_property`). The entity review pages share `group_properties` and lose the same bookkeeping keys.
- The integration merge of `store_extraction_result`: save prompt, record activity, convert, store, rewrite `results_summary`; the `prompt_row` of step 1 feeds both the recorder and the summary rewrite, and the `origin` parameter reaches the recorder through `extract_concept` and the Celery wrapper (`test_the_celery_wrapper_declares_the_pipeline_as_origin`, `test_extract_concept_passes_the_origin_to_storage` pass on the merged `pipeline_tasks.py`).
- The JavaScript. `createConsolidationCard` is the only consumer of the `consolidation` key and takes the run list; the style map carries `merge`, `gate` and `repair`; `summarizeResult` renders the storage pass results (`merges` as labels with a count, `kept_separate` as a count).
