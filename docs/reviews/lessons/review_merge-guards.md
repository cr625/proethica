## Question 2. Behaviour the rules do not name

### Fixed on the review branch

1. **The auto merge folded a row into the kept row through a refused bridge.** `app/services/entity/entity_reconciliation_service.py`, `_auto_merge_exact_matches` (line 456), over the sets of `_exact_match_groups` (line 401). The sets join rows connected by a label or by an IRI, and the fold walked every member against the first row. Scenario: A "Risk State" (matched RiskState), B "Risk State" (IRI and match HazardState), C "Hazard State" (IRI HazardState, unmatched). B was refused against A (matched classes differ), and C, which shares neither label nor IRI with A, was folded into A with basis `label`. On the base, label-only grouping left C alone. A second shape: when the bridge came last in the group, the far row was folded before its bridge, with the basis `label` though the link was the IRI. A third: the kept row was the first row of the set whatever its match, and `merge_entities` carries neither the match columns nor the IRI of the row it deletes, so a set whose unmatched row came first lost the link of its matched row (an outcome of the base too, reached by more folds now that the IRI is a key). Fix: a row joins the kept component only through a label or an IRI the component already holds (the kept row and the rows folded so far), in passes until no row joins; the refused rows and the rows without a direct link form fold sets of their own in the next round; the kept row of a set is its first matched row, else its first row. Tests: `test_a_refused_bridge_does_not_carry_the_rows_behind_it_into_the_kept_row`, `test_a_bridge_processed_last_still_folds_the_set_with_the_basis_of_the_actual_link`, `test_the_kept_row_of_a_fold_set_is_its_matched_row`, `test_rows_matched_to_different_classes_each_keep_their_own_set` (the last passes on the integration tip too and guards the new order).

2. **The rename map left a matched individual typed to a class no row holds.** `_repoint_individual_types` (line 1157) with `_individual_names_existing_class` (line 1146). Scenario: a class row whose match sits below the link band with the decision flag off (the test row 95622 at 0.75, or a column written by the manual match route, `ontserve_ops/matching_ops.py`, which sets the columns and leaves `match_decision` alone) is sent to the model, which reuses the matched class, LegalObligation, the one target L2 admits. The class row moves to `intermediate#LegalObligation`. Its individual carries the same match and was protected from the rename onto that class, so it stayed typed to `intermediate#EnvironmentalStandardsComplianceObligation`, an IRI no class row holds any more; the base repointed it. Fix: a rename onto the matched class of the individual is applied; a rename onto any other class is refused as before (the branch test with the 95603 fixture passes unchanged). Tests: `test_a_rename_onto_the_matched_class_reaches_a_protected_individual`, `test_class_row_and_its_individual_end_on_one_iri_after_a_below_band_reuse`.

3. **Two IRI conventions in the merge stage.** `canonicalize_labels` (line 911, `new_uri = cfg.class_iri(new_label)`), `app/services/extraction/domain_config.py` `class_iri` (line 51, `sanitize`, which keeps hyphens), and the specialization base at line 1067 (`sanitize(entity.entity_label)`). Storage on the integration branch (storage-persistence, L5) mints class rows and individual types with `naming.safe_local_name` (`extraction_graph.pydantic_to_rdf_data` line 115, `individual_type_iri` line 292), the sanitizer of the commit (`class_commit.py` line 85). Scenario: a REUSE of a sheet label with a hyphen; the sheet has eight such canonical labels (Competence Self-Assessment Capability, Judgment Non-Substitution Capability, Self-Review Prohibition Constraint, Expertise-Calibrated Disclosure Principle among them), the prompt block shows them by display label, and the run-48 decision for row 95626 was "Competence Self-Assessment Capability". The canonicalizer wrote `intermediate#CompetenceSelf-AssessmentCapability`, an IRI no store declares, where storage and the commit name `CompetenceSelfAssessmentCapability`. In the merge stage, `rows_by_uri` and the IRI grouping compare exact strings, so the collision veto missed a row holding the storage-minted IRI, `merge_expected_with` was not set, the auto merge did not fold the two rows by IRI, and the repointed individuals carried the hyphenated IRI. Fix: `class_iri` uses `naming.safe_local_name` (its only caller is `canonicalize_labels`), and the specialization base uses the same sanitizer. Tests: `test_class_iri_uses_the_sanitizer_storage_mints_with` (equal to `individual_type_iri` for the same label), `test_a_reuse_of_a_hyphenated_sheet_label_lands_on_the_curated_iri`, `test_a_collision_with_a_storage_minted_iri_is_seen_through_a_hyphenated_label`, `test_a_foldable_holder_with_a_storage_minted_iri_is_flagged_for_the_merge`.

### Reported, not changed

4. **L1 keeps any `matches_existing` row, the commit links at the threshold.** `_matched_class` (line 998) treats a row with `matches_existing` and a `matched_uri` as canonical at any confidence, and a column-only match at or above `MATCH_LINK_THRESHOLD` (0.85). On the integration branch the commit honors a match at or above `match_policy.match_link_threshold()` (default 0.85, `PROETHICA_MATCH_LINK_THRESHOLD`) in `category_resolution._matched_class_override` (line 142) and `class_commit` (line 117). Scenario: a class row matched in the medium band with the flag on (a model match at 0.75, the shape of row 95622 when its flag is on). L1 keeps it out of the canonicalizer, the commit does not honor the match, and the compound label is minted into the extended store. On the base the canonicalizer could reuse the matched class and the commit honored it at 0.75. `MATCH_LINK_THRESHOLD` also ignores the environment override. Proposed: `_matched_class` applies `match_link_threshold()` to the decision path as well, so a below-band row reaches the canonicalizer with L2 restricting its target to the matched class; a deliberate choice of the branch (the commit message names the two conditions), so it is reported.

5. **The extended tier is read from an untracked export.** `app/services/extraction/category_resolver.py`, `ClassHierarchyIndex._build` (line 231) reads `proethica-intermediate-extended.ttl` from the ontologies directory; the OntServe `.gitignore` (line 80) excludes that file, and the clone used here has none, so the index loads 0 extended definitions and `is_strict_subclass(PublicSafetyObligation, SafetyObligation)` is False. In such an environment the D-21 specialization veto and the D-22 collision veto do not fire; with a stale export, classes minted since the export are missed the same way. The dependency is shared with `CategoryResolver` and `RoleAxisResolver` (pre-existing). Proposed: a WARNING when the file is absent, and a note in the deployment docs that the export must follow every commit to the extended store.

6. **The surviving label of a URI-basis fold.** `_pick_preferred_label` (line 1302) keeps the shorter label, so a local-name label ("DisclosureCapability", 20 characters) survives over the display label ("Disclosure Capability", 21); the branch test asserts "disclosurecapability" surviving. With fix 1 the kept row is the matched row, but the label pick is unchanged. Proposed: a fold whose kept row carries `matched_ontology_label` keeps that label; otherwise prefer the label with spaces.

7. **Class-row folds do not retype the individuals of the deleted row.** `merge_entities` (line 239) merges properties and deletes the row; the individuals typed to the deleted IRI (a label fold joins two IRIs, "Confidentiality Obligation (Present Case)" and "Confidentiality Obligation") keep it. The base has the same gap; the L3 IRI folds add nothing to it since the IRI is shared. Proposed: run the rename map {deleted IRI: kept IRI} inside `merge_entities` for class rows.

8. **L5 candidates can duplicate an LLM verdict.** `reconcile_with_review` (line 200) appends the rule candidates and then the LLM verdicts; `reconcile_run` (`entity_review/reconciliation.py` line 121) persists both for the same pair. Proposed: skip an LLM pair a rule already raised, or attach the rule to the verdict.

9. **A rerun overwrites the canonicalization record.** `_reject_canonicalization` (line 1113) and the applied path replace `provenance_metadata['canonicalization']`, so a rerun of the stage on the same unpublished rows loses the earlier record (the D-20 correction asked for the history to be kept with a rejected marker). Proposed: keep a list, newest last.

10. **Published co-holders are invisible to the collision veto.** `_group_for_canonicalization` (line 778) excludes published rows by default, so a target IRI held by a published class row of an earlier run is no collision; the auto merge refuses published rows anyway. Same as the base.

### Checked and found consistent

- The prompts-and-filters block in `_build_canonicalize_prompt` (line 1192) lists the matched rows of the prompt as reuse-only targets; after L1 the only matched rows reaching the prompt sit below the band, and L2 vetoes any other target, so the prompt and the veto agree.
- `run_reconcile_task` writes lists of plain dicts (pairs, rejections with their detail, refusals, candidates with rounded similarity), all JSON-serializable; `provenance.js` `summarizeResult` shows a list as its count. The review route serializes the L5 candidates without `rule`; they reach the page with recommendation `review` and the reason.
- Rows without `entity_uri` skip the IRI grouping and `rows_by_uri`; rows without a label skip the label grouping; a co-holder of another group is refused as `different_group`; a dry run writes nothing and still counts.
- The IRI grouping applies to individual groups as well; two individuals on one IRI share the sanitized label in the case namespace, so the fold agrees with the graph.
- `_same_class` compares normalized local names, so a `matched_uri` stored as a label compares equal to its IRI form; the matcher writes URIs, the manual route writes what the user picked.
- The integration merge of this file (97f1c26) was clean; the diff between the cluster tip and the integration tip is the refactor's `_call_llm` and the prompt block only. `pipeline_tasks.run_reconcile_task` carries the metadata of this branch beside the provenance-surfaces and commit-definitions changes without interaction.
